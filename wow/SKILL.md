# wow

구현된 변경분이나 기존 구조를 보고, 문제 정의와 설계 관점 자체를 다시 잡아 우아한 단순화안을 제안하는 스킬이다.
목표는 코드 줄이기가 아니라 "이렇게 설계했으면 훨씬 단순했겠다"는 감탄이 나오는 재구상이다.

## 불변 규칙

- 파일을 수정하지 않는다.
- 커밋하지 않는다.
- 자동 적용하지 않는다.
- `--go`, `-go` 같은 실행 플래그는 없다.
- 동작 목표는 유지하되 기존 구조는 존중하지 않아도 된다.
- 멋있어 보이는 복잡한 아키텍처를 제안하지 않는다.
- 자잘한 리팩터링, 이름 변경, 단순 중복 제거는 `trim`으로 넘긴다.

## 호출 형태

```text
/wow
```

`/wow`는 제안만 만든다. 적용은 사용자가 별도로 요청할 때만 새 작업으로 다룬다.

## 사고 방식

`trim`은 기존 구현 안에서 군더더기를 다듬는다.
`wow`는 기존 구현의 문제 정의와 설계 모델을 다시 잡는다.

질문은 이렇게 시작한다:

- 이 기능을 처음부터 다시 설계한다면 어떤 개념으로 볼 수 있는가?
- 지금 구조가 문제를 어렵게 만들고 있지는 않은가?
- 상태, 흐름, API, 화면 구조 중 무엇을 다르게 모델링하면 단순해지는가?
- 직접 만든 코드 대신 플랫폼, 프레임워크, 데이터 모델로 해결할 수 있는가?
- 사용자가 경험하는 목표는 유지하면서 내부 개념을 더 적게 만들 수 있는가?

## 분석 순서

1. 현재 repo와 대상 범위를 확인한다.
   - `git status --short`
   - `git diff --stat`
   - `git diff --name-only`
   - 필요하면 `git diff`
2. diff가 없으면 사용자가 보고 싶은 파일, 기능, 브랜치 범위를 묻는다.
3. 기능 목표를 추론한다.
   - 사용자가 얻는 결과
   - 핵심 도메인 개념
   - 현재 구현이 추가한 상태, 파일, 흐름, API 표면
4. 기존 설계의 착각을 찾는다.
5. 새 문제 정의와 새 설계 모델을 만든다.
6. 최소 2개, 최대 4개의 파격적 제안을 낸다.
7. 가장 강한 추천 하나를 고른다.

넓은 구조 분석이 필요하면 Gemini CLI가 있을 때 보조 분석을 맡길 수 있다.

```bash
git diff | gemini -p "이 변경을 더 우아한 모델로 다시 설계한다면 어떤 파격적 단순화가 가능한지 제안해줘. 자잘한 리팩터링 말고 문제 정의와 구조 관점의 전환만 골라줘."
```

Gemini 결과는 참고용이다. 최종 제안은 직접 코드와 diff를 읽고 판단한다.

## 찾아야 하는 제안

좋은 wow 제안은 구현 세부가 아니라 모델을 바꾼다.

- 여러 boolean이나 임시 state를 하나의 도메인 상태 모델로 재정의
- 복잡한 UI 흐름을 단계 나열이 아니라 상태 전이, 라우트, URL, 서버 상태로 재구성
- API 호출 조율 대신 데이터 소유권과 책임 위치를 다시 배치
- 컴포넌트 정리보다 화면의 정보 구조 자체를 다시 설계
- hook/helper 제거보다 hook이 필요 없어지는 데이터 흐름 제안
- 조건문 정리보다 조건이 생기지 않는 도메인 모델 제안
- 직접 만든 캐시, 큐, 동기화, 라우팅을 프레임워크 기능으로 대체
- "미래 확장성" 때문에 커진 구조를 현재 문제의 본질에 맞게 축소
- 여러 레이어가 같은 결정을 반복할 때 결정권자를 하나로 재배치
- 기능을 구현 단위가 아니라 사용자/도메인 개념으로 다시 보기

## 좋은 제안의 기준

- 개념 수가 줄어든다.
- 흐름이 더 자연스러워진다.
- 코드가 문제를 더 직접적으로 표현한다.
- 유지보수자가 보고 "이렇게 생각했어야 했네"라고 느낄 만하다.
- 적용하면 장기적으로 더 단순해진다.
- 리스크와 실험 방법이 구체적이다.

## 나쁜 제안

아래는 wow가 아니다.

- 변수명, 함수명 개선
- helper 추출
- 단순 중복 제거
- 파일 정리만 하는 제안
- 추상화 추가로 더 복잡해지는 제안
- 검증 방법이 없는 큰 구조 변경
- 동작 목표를 바꾸는 제품 제안
- "더 깔끔해 보임" 외 근거가 없는 아키텍처 제안

## 출력 형식

```text
WOW 제안

1. <제안 제목>
   - 지금 설계의 착각:
   - 더 좋은 문제 정의:
   - 새 설계 모델:
   - 왜 단순해지는가:
   - 사용자는 무엇을 그대로 경험하는가:
   - 구현하면 바뀌는 구조:
   - 리스크:
   - 실험 방법:

가장 강한 추천
- ...
```

제안 제목은 과감하고 구체적으로 쓴다.
각 제안은 실제로 적용 가능한 실험 단위를 가져야 한다.

## 중단 조건

아래 상황에서는 제안을 만들기 전에 범위를 묻는다.

- diff나 대상 기능을 찾을 수 없음
- 제품 목표를 전혀 추론할 수 없음
- 사용자가 원하는 동작 보존 범위가 불명확함
- 보안, 결제, 인증, 데이터 삭제처럼 제안만으로도 큰 오해가 생길 수 있는 영역임

중단할 때는 필요한 질문 하나만 한다.
