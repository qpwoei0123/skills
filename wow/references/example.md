# 모범 출력 예시

제안 하나의 밀도 기준이다. 이 수준보다 묽으면 제안을 버린다.

```text
1. 로딩 boolean 3개를 요청 상태 하나로 재정의

   - 지금 설계의 착각: 요청의 진행 상황을 isLoading, isError, isRetrying
     3개의 독립 boolean으로 보고, useEffect 2개로 서로 동기화하고 있다.
   - 더 좋은 문제 정의: 요청은 언제나 정확히 한 상태에만 있다.
     "동시에 참일 수 있는 플래그들"이 아니라 "하나의 상태 기계"다.
   - 새 설계 모델: status: 'idle' | 'loading' | 'error' | 'retrying'
     단일 discriminated union. 파생 값은 렌더 시점에 계산한다.
   - 왜 단순해지는가: 동기화 useEffect 2개와 불가능 상태 4가지
     (예: isLoading && isError)가 삭제된다. 분기마다 "이 조합이
     가능한가"를 고민할 필요가 사라진다.
   - 사용자는 무엇을 그대로 경험하는가: 로딩 스피너, 에러 배너,
     재시도 버튼의 노출 타이밍 전부.
   - 구현하면 바뀌는 구조: 상태 선언 1곳, 전이 함수 1개, 소비처 3곳.
   - 리스크: 재시도 중 이전 에러 메시지를 함께 보여주던 화면이 있다면
     상태에 lastError 필드가 필요하다.
   - 실험 방법: 화면 1개만 새 모델로 바꾸고 기존 테스트를 그대로 돌린다.
```

핵심: 삭제되는 개념(동기화 effect 2개, 불가능 상태 4가지)을 숫자로 말할 수 있어야 wow다.
