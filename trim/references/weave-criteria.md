# 엮기 판정 기준

trim의 엮기 후보를 판정하는 세부 기준이다. 원칙은 하나다: 비슷해서 묶지 않는다. 같은 이유로 변하는 것만 묶는다.

## 같은 이유로 변하는가

- 한 정책·규칙이 바뀔 때 둘 이상의 파일을 항상 함께 고쳐야 하면 같은 이유로 변하는 것이다.
- 한쪽만 따로 바뀔 수 있으면 묶지 않는다.
- 애매하면 묶지 않는다.

## 엮지 말 것

- 모양만 비슷하고 제품 의미나 변경 이유가 다른 코드
- 한 번만 쓰이는 코드를 공통화하는 것
- feature 경계를 넘어서 의존성을 꼬는 것
- 작은 중복을 없애려고 큰 추상화를 만드는 것
- 읽기 쉬운 로컬 코드를 멀리 보내는 것
- UI가 우연히 비슷할 뿐 사용 맥락이 다른 경우
- public API를 바꿔야 하는 공통화
- 순환 import나 역방향 의존성을 만드는 공통화
- 테스트만 통과하고 사람이 읽기 어려워지는 공통화

## 좋은 엮기의 조건

- 엮으면 변경 지점이 실제로 줄어든다.
- 개념 이름과 책임이 더 명확해진다.
- 사용처가 새 구조를 자연스럽게 읽을 수 있다.
- import 경로와 의존성 방향이 더 나빠지지 않는다.
- 테스트와 fixture도 함께 정리된다.
- 나중에 같은 정책 변경이 한 곳에서 끝날 가능성이 높다.

## 적용 전 점검

- import 방향, public API, 테스트 범위가 바뀌지 않는지 확인한다.
- 번들 경계, 라우팅/서버 경계, 스타일 우선순위 변화를 확인한다.
