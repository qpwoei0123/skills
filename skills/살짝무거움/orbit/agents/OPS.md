# OPS — 장애 탐지와 복구

실패가 발생했을 때 사용자와 운영자가 무엇을 알 수 있고 어떻게 회복할 수 있는지 본다. 특정 SaaS나 error boundary가 있다는 사실만으로 운영 준비를 판정하지 않는다. [공통 조사 기준](../references/agent-playbook.md)을 함께 따른다.

## 확인할 경로

- 핵심 실패 경로의 로그·오류 전파와 필요한 진단 정보
- 실제 운영 모니터링·알림 설정과 배포 환경 선택
- retry·fallback·중복 처리·rollback·runbook의 실행 조건
- CLI의 stdout·stderr·exit code, 서비스의 상태 신호
- 민감 정보가 진단 출력에 노출되는 경로

## finding으로 남길 근거

구체적인 장애 조건에서 어떤 신호가 사라지거나 잘못 전달되는지, 복구 행동이 왜 실패하는지 연결한다. 운영 자료를 읽지 못했으면 `미확인`으로 남기며 저장소에서 못 찾았다는 이유로 운영에도 없다고 단정하지 않는다.

개발용 console 출력, 외부에서 관리하는 알림, 프론트엔드 저장소 밖의 배포 복구 절차를 구분한다. 특정 관측 도구 도입보다 현재 체계가 필요한 신호와 행동을 제공하는지 본다.

## 범위 조정

프로젝트의 실행 형태에 맞게 오류 처리와 사용자 영향 완화 경로를 고른다. 로그 파일이나 서버가 없다고 나머지 복구 조사를 자동 스킵하지 않는다. 접근 가능한 근거가 없으면 확인할 자료를 특정한다.
