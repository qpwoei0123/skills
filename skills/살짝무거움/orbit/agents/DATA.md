# DATA — 데이터 계약과 변경 흐름

입력부터 저장·전달·소비까지 데이터의 의미와 정합성이 유지되는지 본다. 별도 DTO·adapter·상태관리 도구의 유무는 결함 기준이 아니다. [공통 조사 기준](../references/agent-playbook.md)을 함께 따른다.

## 확인할 경로

- 외부 입력, schema·검증과 실제 사용 위치
- 동일 데이터의 여러 사본, 갱신·무효화·동기화 경로
- 파생 값의 저장 이유와 변경 이후 일관성
- API·event·DB·UI 사이 필드 의미와 호환 계약
- migration, backfill, 부분 실패, 동시 변경과 rollback 조건

## finding으로 남길 근거

어떤 입력·순서·실패 조건에서 값이 어긋나는지, 잘못 노출·저장되거나 기존 소비자가 깨지는지 확인한다. 같은 데이터의 중복 저장도 의도된 cache·snapshot·비정규화라면 갱신 계약과 trade-off를 함께 본다.

서버 응답을 그대로 사용하거나 ORM 결과를 반환해도 공개 계약에 맞으면 변환 계층을 요구하지 않는다. 반대로 타입 이름이 같아도 검증·직렬화·노출 범위가 맞는지는 확인한다.

반복 쿼리는 실제 호출 경로와 데이터 증가에 따른 비용을 확인한다. `루프 안 쿼리`만으로 영향이나 시급성을 단정하지 않는다. N+1과 입력 검증 누락처럼 원인·수정이 다른 문제는 별도 finding이다.

## 범위 조정

프론트엔드는 query cache·component state·form·URL 상태도 본다. 백엔드는 저장·query·직렬화·event 계약을 본다. library·CLI도 상태나 파일·데이터 변환이 있으면 조사한다. 데이터 흐름 자체가 없는 경우에만 해당 범위를 스킵한다.
