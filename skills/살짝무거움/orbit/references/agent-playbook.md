# 공통 조사 기준

선택한 view가 무엇이든 문제의 성립 조건과 반례를 실제 코드·설정에서 확인한다.

## finding의 최소 근거

claim은 하나의 문제를 설명해야 하고 직접 읽은 `file:line`, 실제 영향 경로, 다음에 확인하거나 바꿀 위치가 있어야 한다. 위임된 조사자는 사실을 반환하며 최종 선별자가 점수를 붙인다.

스타일 취향, 특정 폴더 구조를 선호한다는 이유, 파일이나 테스트가 없다는 사실만으로 결함을 만들지 않는다. 저장소의 명시적 계약이나 관찰 가능한 실패·유지보수 비용과 연결한다. 의도한 trade-off로 보이더라도 실제 계약 위반이나 영향이 있으면 그 근거를 설명한다.

진입점·설정에서 필요한 호출자·소비자·검증 경로로 따라간다. source와 generated 결과가 다르면 생성 입력과 실제 사용되는 결과를 함께 확인한다. vendor·binary·build 산출물을 일괄 정독하지 않되 해당 계약의 근거이면 제외하지 않는다.

## 설정의 선언과 실제 사용

경로·버전·환경 설정의 불일치를 주장하려면 선언 위치와 실제 도구 호출·환경을 함께 읽는다. CLI 플래그뿐 아니라 환경변수, 설정 파일, 작업 디렉터리, OS·도구 버전이 기본값을 바꿀 수 있다.

도구 기본 경로를 기억에 의존해 단정하지 않는다. 현재 버전의 설정 조회, `--help`, 공식 문서로 필요한 값을 확인한다. 경로 차이만으로 문제라고 하지 말고 캐시 미사용, 산출물 누락, 다른 환경 실행처럼 결과에 미치는 영향을 확인한다.

## 반례와 불확실성

반례가 같은 revision과 실행 조건을 가리키는지 확인한다. 다른 환경의 설정, 실행되지 않는 테스트, 오래된 generated 결과가 현재 경로를 반증하는 것처럼 섞이지 않게 한다.

반례가 claim을 뒤집으면 철회하고 조건만 바꾸면 범위를 좁힌다. 근거가 해결되지 않으면 불확실성을 남긴다. 반박자가 없다는 이유로 confidence를 높이지 않는다.

## 다음 행동

`next_step`에는 실제로 필요한 파일·식별자와 행동을 적는다. `구조 개선`, `테스트 보강`처럼 대상이 없는 표현을 피한다. 필요한 검증이 있으면 연결하되 점수를 높이려고 명령어를 덧붙이지 않는다.

좋은 예: `src/features/auth/model/store.ts`의 `persistSession`과 호출자를 확인해 중복 저장이 필요한 계약인지 판단한다.

actionability의 합산 방식은 [pipeline_contracts.py](../scripts/pipeline_contracts.py), 채점 해석은 [결과 계약](execution-lifecycle.md)을 따른다. 그 숫자가 다음 행동의 타당성을 대신하지 않는다.

## 범위 축소

주된 조사 대상이 없으면 해당 view의 인접 경로로 의미 있는 확인이 가능한지 본다. 이 view와 무관하면 스킵하고 이유만 남긴다. 발견 수를 채우기 위해 다른 관점의 사소한 문제를 끌어오지 않는다.
