# 저장소 유형에 맞춰 조사하기

실제 실행·배포·소비 구조를 기준으로 조사 경로를 고른다. 하나의 저장소에 여러 유형이 공존할 수 있다. 아래는 출발점이며 특정 계층 구조나 도구 도입을 정답으로 강제하지 않는다.

| 확인한 구조 | 우선 볼 경로 | 피할 가정 |
|---|---|---|
| 프론트엔드 | route·화면·API client·상태·배포 | 폴더 이름만으로 FSD 채택, 상태관리 도구 필수 |
| 백엔드 | request·job·event 진입점, 입력 검증, 저장과 직렬화 | controller·service·repository 계층이 반드시 분리돼야 함 |
| Monorepo | workspace 설정, 실제 package 의존·공개 계약, task graph | 모든 package가 같은 toolchain·배포 방식을 가져야 함 |
| 여러 서비스 | 실제 네트워크·event·DB 경계, 배포·관측·호환 기간 | 같은 repo라는 이유로 하나의 배포 단위로 봄 |
| Library | 공개 API·exports, 지원 환경·peer 계약·소비자 | 앱의 버전 고정 규칙과 운영 체계를 그대로 적용 |
| CLI | command 입력, 설정·파일 I/O, exit code·출력 계약 | UI가 없다는 이유로 데이터·운영 관점을 생략 |
| 정적 사이트·문서 | 콘텐츠 생성·배포, 링크·asset·외부 script | 이름이 정적이라는 이유로 상태·빌드 코드가 없다고 단정 |

Node·Python·Go·Rust·Java 등의 도구별 manifest·lockfile·checksum 파일은 목적이 다르다. 특정 파일의 존재나 버전 범위 문법만으로 재현성을 판정하지 않고 실제 설치·빌드·배포 명령과 지원 계약을 확인한다. 정확한 도구 동작이 필요하면 현재 버전의 공식 근거를 확인한다.

큰 저장소는 사용자의 범위와 변경 영향이 큰 경로부터 조사한다. 일부 package만 봤으면 그 범위를 보고한다. 관찰 도중 다른 실행 형태가 드러나면 유형과 조사 범위를 갱신하고, 처음 붙인 분류를 지키기 위해 관련 경로를 스킵하지 않는다.
