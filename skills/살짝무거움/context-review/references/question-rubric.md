# 고맥락 질문 판정 기준

후보 질문을 만들었을 때만 읽는다. 목적은 좋은 문장을 만드는 것이 아니라 사람이 답해야 할 결정만 남기는 것이다.

## 필수 관문

다음 중 하나라도 실패하면 제출하지 않는다.

| 관문 | 통과 질문 | 탈락 질문 |
|---|---|---|
| 근거성 | 변경·문서의 구체적 사실을 가리킴 | 일반론이나 추측에서 시작함 |
| 고맥락성 | 제품 정책·운영 현실·데이터 약속·소유권이 필요함 | 코드·테스트·config로 답할 수 있음 |
| 의사결정성 | 답에 따라 병합·범위·전환·관측·후속이 달라짐 | 답을 받아도 행동이 같음 |
| 단일성 | 대상·상황·조건과 한 결정이 선명함 | 여러 주제를 한꺼번에 물음 |
| 신규성 | 본문·자료·댓글에 답이 없음 | 이미 답했거나 다른 질문과 중복됨 |

질문이 구현의 세부 형태가 바뀌어도 남는지 확인한다. 코드 재작성만으로 사라지는 질문은 고맥락 질문이 아니다.

## 탐색 관점

아래를 체크리스트처럼 하나씩 채우지 않는다. 변경 지도에서 실제 영향이 확인된 관점만 사용한다.

- **제품 의도**: 성공 기준, 사용자 약속, 정책상 예외, 의도적으로 버린 경험
- **도메인·계약**: 바뀌지 않아야 할 불변조건, 외부 소비자, 버전 호환 기간
- **데이터**: backfill, dual read/write, 정합성 기준, 보존·삭제, 되돌릴 수 없는 변환
- **운영**: 실패 시 사용자 영향, 탐지 신호, on-call 행동, 용량·비용 한계
- **롤아웃**: 순서, flag, 부분 배포, rollback 가능 시점, 중단 기준
- **보안·정책**: 권한 경계, abuse, 개인정보, 감사·규제 요구
- **소유권**: 여러 팀 사이 결정권, 후속 작업, migration 종료 책임
- **트레이드오프**: 버린 대안, 미래 제약, 예외를 받아들인 이유

## 우선순위

다음 순서로 상위 질문만 남긴다.

1. 영향받는 사용자·데이터·시스템 범위가 큼
2. 답이 없으면 되돌리기 어려운 결정을 하게 됨
3. 현재 자료 사이 모순이나 중요한 공백이 큼
4. rollout·rollback·관측 안전장치가 약함

심각도나 확신도 점수는 붙이지 않는다. 질문은 finding이 아니다. 대신 답변이 필요한 시점을 `병합 전 | 배포 전 | 후속`으로 표시한다.

## 질문 공식

```text
<관찰된 변경>이 <영향받는 사용자·시스템·계약>을 바꿉니다.
<구체적 상황>에서 유지해야 할 <정책·불변조건·종료 기준>은 무엇인가요?
```

해법을 먼저 정해 놓고 동의를 구하지 않는다. 답이 단순 yes/no로 끝나면 어떤 기준이나 선택을 알아야 하는지 다시 쓴다.

## 나쁜 질문을 고치는 예

```text
나쁨: 롤백 계획이 있나요?
좋음: 새 상태를 기록한 뒤 구버전 worker가 이를 읽지 못하는 구간이 생깁니다.
      혼합 버전 배포 중 반드시 유지해야 할 처리 규칙과 rollback 가능 시점은 언제인가요?
```

```text
나쁨: 모니터링은 충분한가요?
좋음: 새 추천 기본값이 대상 사용자 범위를 넓히지만 연결 문서에는 중단 기준이 없습니다.
      어떤 제품 지표와 guardrail을 기준으로 rollout을 계속하거나 중단하나요?
```

예시는 문장 구조만 참고한다. 실제 근거가 없는 worker, 지표, rollout을 질문에 끼워 넣지 않는다.

## 0개와 검토 불완전

다음을 모두 확인하고도 통과 후보가 없으면 0개로 끝낸다.

- PR/MR 본문과 의미 변경 diff
- 직접 연결된 issue·spec·ADR
- 관련 contract·test·migration·배포 자료
- 제품 계약, 데이터 불변조건, 운영 실패, rollout·rollback, 관측, 소유권 중 실제 영향 관점

모든 후보가 `이미 답함 | 비중요 | 코드로 답 가능 | 중복` 중 하나로 탈락했음을 내부적으로 확인한다.

자료 접근 실패나 링크 누락은 0개가 아니다. 이때는 `검토 불완전`으로 끝내고 빠진 자료와 제한된 판단만 적는다.
