# won-ship

현재 작업을 리뷰받을 상태로 마무리한다. `good`, `commit`, `mr`의 판단 기준을 재사용하고, 이 스킬은 전체 범위와 단계 연결, 기존 Draft 갱신을 맡는다.

## 요청과 실행

- `$won-ship`, `/won-ship`, "출항해줘"는 코드 정리부터 커밋·push·Draft 생성 또는 기존 Draft 본문 갱신까지 완료한다.
- "계획만", "수정하지 말고"이면 읽기 전용 조사로 범위와 정리·커밋 계획, 제목·본문 수정안을 만든다. 파일·git·원격 변경은 수행하지 않는다.
- `--go`, `-go`는 기존 실행 표기로 지원하며, 명시적인 계획·범위 제한을 우선한다.
- 요청한 범위와 이를 다듬으며 생기는 변경에는 같은 요청의 승인을 적용한다. 하위 단계마다 다시 묻지 않는다.
- branch rename, force push, 일반 PR/MR 생성과 기존 Draft의 제목·상태·리뷰어·라벨 변경은 포함하지 않는다.

## 1. 대상과 범위

1. git 충돌, staged·unstaged·untracked, 현재 branch와 원격 저장소를 확인한다. detached HEAD나 default branch에서는 진행하지 않는다.
2. 사용자 지정 base → `branch.<name>.gh-merge-base` → 원격 기본 branch → `main` → `master` 순으로 base를 정한다. 현재 branch의 원격 추적 ref를 base로 쓰지 않는다.
3. 기여 문서와 플랫폼을 확인하고, 인증된 `gh`/`glab`을 우선해 같은 source repository·head branch의 열린 PR/MR을 조회한다. push에는 CLI 인증을 쓸 수 있는 HTTPS 경로를 확인하며, SSH를 먼저 시도하거나 원격 URL·전역 git 설정을 임의 변경하지 않는다.
4. 열린 요청이 없으면 `새 Draft`, 정확히 하나의 열린 Draft가 있으면 `기존 Draft + ID`로 고정한다. 일반 PR/MR이거나 대상이 여럿이면 멈추고 대상을 확인한다.
5. 기존 Draft는 [references/draft-update.md](references/draft-update.md)에 따라 snapshot과 편집 권한을 확인하고, 그 target branch를 base로 사용한다. 사용자 지정이나 기여 규칙과 충돌하면 먼저 해소한다.
6. base에 없는 커밋과 현재 작업의 미커밋 변경을 합쳐 리뷰 범위를 정한다. 둘 다 없으면 `출항할 변경 없음`으로 종료한다. 무관한 변경을 안전하게 분리할 수 없으면 범위를 묻는다.

선택한 경로와 범위는 완료까지 유지한다. 기존 Draft가 사라졌다고 새 Draft 생성으로 전환하지 않는다. 실행 중 사용자나 다른 프로세스가 범위 파일을 바꾸면 덮어쓰지 않는다.

## 2. 정리와 커밋

필요한 단계에서 해당 `SKILL.md`를 읽고 현재 범위와 실행 의도를 전달한다. 필요한 하위 스킬이 없으면 이름을 보고하고 진행하지 않는다.

1. `good`에 전체 리뷰 범위를 전달해 코드와 필요한 맥락을 다듬는다. 이미 실행한 검증과 원본 상태를 전달해 같은 조사를 반복하지 않게 한다.
2. 정리할 코드나 남길 주석이 없으면 그대로 진행한다. 검증이 실패했으면 커밋·원격 변경으로 넘어가지 않는다.
3. dirty worktree가 있으면 `commit`으로 의미 단위 커밋을 만든다. 기존 커밋만 있으면 새 커밋이나 amend 없이 진행한다.
4. 남은 변경이 없는지 확인하고 최종 `<base>...HEAD`를 리뷰한다. commit hook 등으로 검증한 코드가 달라졌으면 관련 검증을 다시 실행하고, 같으면 결과를 재사용한다.
5. 심각한 결함·비밀 정보·요청 밖 변경은 push 전에 해소한다. 이미 성공한 로컬 단계를 후속 실패 때문에 일괄 rollback하지 않는다.

### 이번 변경에서 추가된 테스트

검증 근거를 만들려고 테스트를 새로 작성하지 않는다. base에는 없고 이번 리뷰 범위에서 추가된 테스트 중 구현 분기·mock 반환값·기존 검증을 반복하거나 실제 입력 계약에 없는 사례만 다루는 것은 정리 후보가 될 수 있다.

독립적인 회귀 방지 가치가 없다는 근거를 코드와 기존 테스트에서 확인할 때만 `good`에 삭제 후보로 전달한다. 외부 계약·과거 버그·중요한 경계값을 보호하는 테스트와 base에 있던 assertion은 보존한다. 작성 주체를 삭제 근거로 삼지 않는다. 이 예외는 해당 리뷰 범위의 신규 테스트에만 적용한다.

## 3. Draft 준비와 제출

`mr`의 제목·본문 규칙을 사용해 원격 변경 전에 완성된 결과를 준비한다. 실행 요청이면 변경 범위를 알린 뒤 같은 승인으로 이어가고, 계획 요청이면 수정안을 보여주는 것으로 끝낸다.

won-ship이 작성하는 요약·검증·리뷰 설명은 `<!-- ship:managed:start -->`와 `<!-- ship:managed:end -->` 사이에 둔다. 실제로 필요한 내용만 포함한다.

- **새 Draft:** `mr`에 고정한 base/head·리뷰 범위·완성된 제목/본문·검증 결과를 전달해 push와 생성을 맡긴다. won-ship에서 먼저 push하거나 mr에서 정리·커밋·검증을 중복 실행하지 않는다. 진행 중 같은 source/head의 요청이 생기면 생성하지 않고 현재 상태와 URL을 보고한다.
- **기존 Draft:** [references/draft-update.md](references/draft-update.md)의 snapshot 확인·push·본문 갱신 절차를 수행한다. 이 경로에서는 새 Draft를 만드는 mr 실행을 하지 않는다.

완료 후 Draft 상태, source/target, remote head SHA와 본문 반영을 확인한다. push 거절이나 원격 실패가 나면 이미 완료한 commit·push를 정확히 구분한다.

## 보고

변경 요약, 커밋, Draft URL과 생성·갱신 여부, 필요한 검증 결과를 간결하게 보고한다. 중단했으면 실제 원인과 완료된 로컬·원격 상태, 필요한 다음 행동을 덧붙인다. 빈 단계와 형식적인 위험·검증 목록을 채우지 않는다.
