# 사람이 결정할 질문의 경계

후보가 코드로 해결할 의문인지, 사람이 결정해야 할 문제인지 애매할 때 읽는다.

## 질문으로 남길지 판단하기

| 관찰한 상황 | 처리 |
|---|---|
| 기본값이 바뀌었지만 어떤 호출자에 적용되는지 아직 모름 | 호출자·설정을 읽어 먼저 확인한다. |
| 기본값이 기존 고객에게도 적용되는데 기획은 신규 고객만 설명함 | 기존 고객에게 유지할 정책을 묻는다. 답에 따라 적용 조건이나 전환 작업이 달라진다. |
| 유효한 입력에서 새 분기가 확실히 예외를 던짐 | 확인된 결함으로 알린다. 이 동작에 동의하는지 묻지 않는다. |
| 기존 댓글에서 적용 대상을 결정했고 현재 코드에도 맞음 | 이미 답한 질문이므로 제외한다. |
| 기존 결정과 현재 구현이 충돌함 | 같은 질문을 반복하지 않고, 어느 근거와 동작이 충돌하는지 밝혀 재확인한다. |

코드가 구현한 동작 자체는 정책이 옳다는 근거가 아니다. 반대로 기획서에 설명이 없다는 이유만으로 미결정이라고 단정하지 않는다. 관련 구현과 기존 답변에도 기준이 없는지 확인한다.

## 질문을 구체화하기

질문은 실제로 바뀐 사용자 경험이나 계약에서 시작한다. 영향이 있는 경우에만 데이터의 보존·전환, 권한, 배포·되돌리기, 운영 책임 같은 관점을 더 살핀다. 분야별 질문을 채우거나 가상의 위험을 만들지 않는다.

```text
약함: 롤백 계획이 있나요?
구체적: 새 상태를 기록하면 구버전 worker가 해당 데이터를 읽지 못합니다.
        구버전으로 되돌릴 수 있어야 하는 기간은 언제까지인가요?
        답에 따라 새 상태 기록을 시작할 시점과 호환 처리가 달라집니다.
        근거: <확인한 코드·기존 운영 결정>
```

예시의 사실을 그대로 가정하지 않는다. 답을 유도하는 해법이나 단순 승인 요청 대신 필요한 정책·조건을 묻는다. 답변 시점과 담당 역할은 실제 진행에 도움이 될 때만 붙인다.

## 질문 없음과 자료 부족

관련 변경과 접근 가능한 자료를 확인했는데 미결정이 없다면 질문 없이 끝내도 된다. 질문 수를 맞추기 위해 사소한 의문을 올리지 않는다.

핵심 diff를 읽지 못했거나, 실제 결정을 담은 문서에 접근하지 못해 의도를 판단할 수 없다면 검토가 불완전하다. 빠진 자료와 제한된 판단을 밝힌다. 관련 없는 링크 하나가 열리지 않는다는 이유로 전체 검토를 실패로 취급하지 않는다.
