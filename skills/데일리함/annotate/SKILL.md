# annotate

현재 작업에서 코드만으로 드러나지 않는 이유와 제약만 짧은 한글 주석으로 남긴다. 목표는 주석 수가 아니라 다음 독자의 이해 시간 단축이다.

## 계약

- 동작을 바꾸지 않는다. 코드 수정이 필요하면 보류한다.
- 현재 diff와 이를 이해하는 주변 로직만 다룬다. 사용자가 범위를 지정하면 그 범위를 우선한다.
- 코드가 이미 설명하는 내용, 추측성 규칙, 금방 낡을 구현 상세는 쓰지 않는다.
- 기존 주석의 언어, 위치, 한 줄·블록 사용 습관을 따른다.
- 주석 수정 권한과 승인 상태는 현재 요청에만 유효하다. 다음 작업에서 명시 요청이 없으면 주석을 추가하지 않는다.

## 호출

```text
/annotate
/annotate --go
/annotate -go
```

- 기본 호출은 후보와 검증 계획만 제안한다.
- `--go`, `-go`는 위험도 `낮음` 후보만 바로 반영한다.

## 연계 요청

- 코드 정리와 주석을 함께 요청하면 `trim`이 전체 수정 흐름을 맡는다.
- `trim`의 검증이 끝난 최종 diff에만 `annotate`를 실행한다. 정리 과정에서 사라질 코드에 먼저 주석을 달지 않는다.
- 주석만 요청받았으면 `trim`을 자동 실행하지 않는다.

## 흐름

1. `git status --short`, `git diff --stat`, `git diff --name-only`로 범위를 정한다. diff도 지정 범위도 없으면 질문 하나만 한다.
2. 필요한 diff와 호출부·상태 전이·권한·캐시·외부 API 경계를 읽는다.
3. 주변 파일의 기존 주석 스타일을 확인한다.
4. 후보마다 남길 맥락, 필요 이유, 제안 문구, 위험도를 적는다.
5. 기본 호출이면 계획에서 멈추고, `--go`면 낮은 위험도 후보만 적용한다.

## 후보 판정

남긴다:

- 제품 정책이나 외부 제약 때문에 분기·순서·우회가 생김
- 캐시, 권한, 이벤트, 상태 전이처럼 숨은 맥락이 있음
- 같이 수정해야 할 파일이나 테스트 관계가 코드만으로 보이지 않음
- 설명이 없으면 같은 실수를 반복할 가능성이 큼

남기지 않는다:

- 함수명, 변수명, 코드 흐름을 그대로 반복함
- 담당자·제거 조건 없는 TODO/FIXME를 새로 만듦
- 제품 규칙을 추측해야 함
- 주석보다 작은 리팩터링이 이해를 더 직접적으로 개선함

좋은 예:

```ts
// 초대 토큰은 재사용되면 안 되므로 조회와 동시에 만료시킨다.
```

## 응답 형식

```text
주석 후보

1. <후보 제목>
   - 위치:
   - 남길 맥락:
   - 왜 필요한가:
   - 제안 주석:
   - 위험도: 낮음 | 중간 | 높음

보류한 후보
- <보류 이유>

검증
- 실행 예정:
- 생략:
```

## `--go` 실행

1. 적용 전 diff stat과 가능한 검증 명령을 기록한다.
2. 낮은 위험도 주석만 반영한다.
3. diff에서 주석 외 동작 변경이 없는지 확인한다.
4. 주석에 영향을 받는 lint·format만 실행한다.
5. 반영 위치, 보류 후보, 검증 결과를 보고하고 annotate intent를 종료한다.

## 중단

아래에서는 수정하지 않고 이유와 필요한 다음 행동을 보고한다.

- 범위가 불명확함
- 기존 주석과 충돌하는 규칙을 확정할 수 없음
- 제품·운영 규칙을 추측해야 함
- 사용자의 기존 변경과 주석 대상이 안전하게 분리되지 않음
