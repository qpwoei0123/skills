# 리뷰 요청 제목과 본문

PR/MR 제목과 본문을 만들 때 읽는다. 기여 문서의 명시 규칙이 항상 우선한다.

## 제목

별도 규칙이 없으면 Conventional Commits 형식을 쓴다.

```text
<type>[(<scope>)]: <한글 요약>
```

판단 순서:

1. 현재 브랜치의 대표 커밋
2. 최근 PR/MR 제목
3. 최근 git log
4. 변경 도메인

- 최근 리뷰 요청이 scope를 일관되게 쓰고 변경 범위가 명확할 때만 scope를 붙인다.
- 주변 제목이 비정형이어도 의미만 참고하고 형식은 정규화한다.
- 요약에는 변경 결과를 쓰고 마침표를 붙이지 않는다.

## 본문 근거

다음 순서로 구조를 고른다.

1. 레포 PR/MR 템플릿
2. 최근 PR/MR 본문 2~3개의 섹션·체크리스트·검증 표기
3. 현재 커밋과 diff
4. 기본 템플릿

확인할 템플릿:

- `.github/pull_request_template.md`
- `.github/PULL_REQUEST_TEMPLATE.md`
- `.github/PULL_REQUEST_TEMPLATE/*.md`
- `.gitlab/merge_request_templates/*.md`

목록만 보고 최근 본문 구조를 확인했다고 판단하지 않는다. 본문을 볼 수 없으면 실패 이유를 계획에 남기고 기본 템플릿을 사용한다.

## 기본 템플릿

```md
## 요약
-

## 변경 사항
-

## 검증
- [ ]

## 리뷰 포인트
-

## 리스크
-
```

## 작성 기준

- 레포 템플릿의 필수 섹션과 체크리스트를 삭제하지 않는다.
- diff 나열보다 왜 이 접근을 택했는지 먼저 설명한다.
- 버린 대안이 중요하면 한 줄로 남긴다.
- 리뷰어가 집중할 파일과 위험 지점을 `리뷰 포인트`로 좁힌다.
- rename, import 정리 같은 기계적 변경은 한 줄로 묶는다.
- 실행한 검증은 완료로 표시하고, 실행하지 못했으면 이유를 적는다.
- 리스크가 낮아도 `낮음`처럼 명시한다.
