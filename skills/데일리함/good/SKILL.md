## 공통 판단 기준

현재 요청과 이 스킬의 작업 범위 안에서 관련 있는 기준만 적용한다. 규칙을 충족하려고 요청 밖 수정이나 형식적인 보고 항목을 추가하지 않는다.

현재 동작을 보존하는 코드·주석 정리에 적용한다. 주석만 요청받으면 코드 구조를 바꾸지 않는다.

### 한 번에 다루는 맥락 줄이기

함께 실행되지 않는 분기와 서로 다른 목적의 로직이 교차하면 책임별로 분리한다. 구현 상세를 숨길 때는 호출부에서 목적을 이해할 수 있는 이름과 경계를 선택한다. 단순히 함수가 길다는 이유만으로 나누지 않는다.

### 시점 이동 줄이기

동작을 이해하기 위해 여러 함수·파일을 왕복해야 하는지 본다. 단순한 정책은 사용처에서 위에서 아래로 읽히게 표현하고, 추상화가 필요한 경우에도 핵심 흐름은 호출부에 드러낸다.

### 조건과 숫자의 의미 드러내기

복잡한 조건과 맥락 없는 숫자에는 의도를 설명하는 이름을 붙인다. 중첩된 삼항식은 조건의 순서가 보이도록 펼친다. 이미 자명한 한 줄 표현을 이름 붙이기만 위해 분리하지 않는다.

### 숨은 부수효과 확인하기

조회·검증처럼 보이는 호출에 로깅·상태 변경·화면 종료가 숨어 있는지 확인한다. 수정하는 작업에서는 호출부나 명시적인 책임으로 드러내되, 실행 순서·실패 전파·관측 동작을 보존한다. 읽기 전용 작업에서는 실제 영향과 의도된 동작인지 판단하는 근거로 사용한다.

### 이름과 동작 일치시키기

이름·입력·출력으로 실제 동작을 예상할 수 있는지 본다. 기존 라이브러리와 동작이 다른 래퍼는 추가 책임을 드러내는 이름을 사용한다. 이름을 맞추려고 공개 계약을 임의로 바꾸지 않는다.

### 같은 역할의 반환 형태 맞추기

같은 역할의 함수·Hook은 반환 형태를 일관되게 유지한다. 데이터와 조회 상태 객체, boolean과 결과 객체를 혼용해 호출자가 내부 구현을 확인해야 하는지 본다. 의도된 계약 차이는 보존하고, 변경할 때는 기존 호출자의 의미를 확인한다.

### 변경 단위에 맞춰 경계 정하기

함께 수정·삭제되는 코드는 가까이 두고, 기능보다 파일 종류만으로 흩어 놓지 않는다. 폼도 필드가 독립적으로 변하는지, 필드 간 정책이 함께 변하는지에 따라 검증 경계를 정한다. 기존 import 방향·공개 계약·번들·라우팅·서버 경계와 스타일 우선순위를 유지한다.

### 함께 변경되는 단위 파악하기

같은 정책을 바꿀 때 반드시 함께 수정되어야 하는 부분을 찾는다. 코드와 사용처·설정·검증·공유 상수의 관계를 확인하고, 한쪽만 변경되면 깨지는 단위를 함께 다룬다. 모양이 비슷하다는 이유만으로 같은 변경 단위라고 판단하지 않는다.

### 변경 영향과 전달 계층 줄이기

공유 함수나 상태를 바꿀 때 영향받는 호출자와 화면을 확인한다. 같은 기술을 사용한다는 이유로 서로 다른 책임을 한 함수에 모으지 않는다. 값을 전달만 하는 중간 계층은 조합으로 줄일 수 있는지 보고, 실제 역할을 표현하는 props는 유지한다. 공유 상태·Context 도입은 필요한 소비 범위와 의존성이 명확할 때 선택한다.

### 독립적인 변경 보존하기

공통화는 같은 이유로 변하는 코드에 적용한다. 제품 의미가 다르거나 독립적으로 바뀌는 코드는 중복을 허용한다. 작은 중복을 없애려고 더 큰 추상화·순환 참조·역방향 의존성을 만들지 않는다. 함께 바뀌지 않으면 오류가 나는 경우에는 응집도를, 독립적인 경우에는 읽기 쉬움과 좁은 변경 범위를 우선한다.

# .⚡good

현재 변경을 다음 사람이 읽고 수정하기 좋게 다듬는다.

설계 모델 재검토는 `.⚡wow`, 버그 찾기는 별도 코드 리뷰로 다룬다.

## 요청과 범위

- `$.⚡good`, `/.⚡good`과 코드 정리·주석 실행 요청은 해당 작업을 완료한다. "후보만", "계획만"이면 수정 없이 제안한다. `--go`, `-go`도 실행 표기로 받지만 사용자가 명시한 계획·범위 제한을 우선한다.
- "주석만"이면 주석만 수정하고, "코드만" 또는 "주석 추가 없이"이면 주석을 추가하지 않는다.
- 사용자가 지정한 파일·모듈·리뷰 범위를 우선한다. 지정이 없으면 현재 staged·unstaged·untracked 변경을 보고, worktree가 깨끗하면 사용자가 정한 base 또는 원격 기본 branch 대비 현재 branch의 변경을 본다.
- 대상이 없거나 서로 다른 작업이 섞여 범위를 정할 수 없을 때만 묻는다. 일반적인 칭찬이나 문서 다듬기 요청으로 실행하지 않는다.

## 판단 기준

코드로 의도를 더 직접 표현한 뒤, 그래도 드러나지 않는 이유와 제약만 주석으로 남긴다.

- 계산 가능한 중복 상태, 효과보다 비용이 큰 캐시, 실제 입력 계약상 불필요한 분기를 줄인다.
- 공개 API·데이터 계약·UX·접근성·테스트의 보장 수준을 유지하고 테스트 assertion을 정리 대상으로 바꾸지 않는다. 입력 중간값, optimistic update, debounce처럼 시간 의미가 있는 상태를 단순한 중복으로 판단하지 않는다.
- 변경에 영향을 받는 평가 순서, null과 falsy, 예외 전파, async timing, 객체 identity를 확인한다. 타입 검사나 lint 통과만으로 전체 동작이 보존된다고 판단하지 않는다.
- 주석은 코드만으로 알기 어려운 제품 정책, 외부 제약, 순서의 이유, 함께 바꿔야 하는 관계에 한정한다. 짧은 한글을 기본으로 하되 사용자 지시와 저장소 관례를 따른다.
- 이름과 코드를 반복하는 설명, 추측한 정책, 금방 낡을 구현 상세, 제거 조건 없는 TODO는 추가하지 않는다.

예: `// 초대 토큰의 재사용을 막기 위해 조회와 동시에 만료시킨다.`

설계 모델을 바꿔야 얻는 개선은 별도로 설명한다. 현재 동작을 보존하라는 요청을 재설계로 확대하지 않는다.

## 수정과 확인

1. 필요한 diff와 호출부·입력 계약을 읽고, 이번 수정이 바꿀 수 있는 동작과 확인 방법을 정한다. 이미 실행한 검증이 현재 코드에도 유효하면 재사용한다.
2. 첫 수정 전에 대상 파일의 원본·존재 여부·종류와 git index 상태를 기록해 자신의 변경만 복원할 수 있게 한다. untracked도 포함하며, 백업은 저장소 밖 임시 경로에 둔다.
3. 근거가 충분한 변경을 적용한다. 근거가 부족한 후보는 보류하고, 주석은 정리가 끝난 코드에만 남긴다.
4. 변경과 직접 관련된 기존 검증을 실행한다. 주석만 바꿨다면 동작 diff가 없는지와 필요한 lint·format만 확인한다.
5. 실패하면 자신의 변경만 복원한다. 동시 사용자 변경과 구분할 수 없으면 덮어쓰지 말고 해당 부분을 보고한다.

git index와 기존 staged·unstaged·untracked 작업을 보존한다. 이 스킬에서 `git add`, `git rm`, `git restore`, `git checkout`, `git reset`으로 상태를 재구성하지 않는다. 안전하게 복원할 수 없거나 기존 검증 실패 때문에 동작 보존을 판단할 수 없으면 해당 수정을 보류한다.

## 보고

무엇이 읽고 수정하기 쉬워졌는지, 필요한 검증 결과, 남은 중요한 보류 사항을 간결하게 전한다. 개선할 것이 없으면 그대로 말한다. 후보 등급표나 빈 보고 항목을 채우지 않는다.
