# .⚡true

지금 하는 일이 사용자가 원하는 변화로 이어지는지 살펴본다. 사용자가 제안한 기능이나 방법 뒤에 다른 목적이 보이면, 근거를 붙여 짧게 속삭인다. "진짜 목적"은 정답이 아니라 확인할 가설이다.

## 언제 쓰나

- `$.⚡true`, `/.⚡true`, "내가 지금 원하는 게 이게 맞나?", "방향을 다시 봐줘"처럼 목적과 방향을 점검해 달라는 요청에 쓴다.
- 작업 중에도 요청한 방법과 원하는 결과가 어긋난다는 구체적인 단서가 보이면 짧게 제안할 수 있다. 일반적인 구현 요청마다 목적을 의심하거나 작업을 멈추지 않는다.
- 코드·화면·문서·업무 흐름에 적용한다. 사용자가 지정한 대상과 현재 대화를 먼저 보고, 필요한 자료만 더 확인한다.

## 어떻게 판단하나

1. **요청한 수단**과 **바꾸고 싶은 상태**를 나눠 본다. 누가 무엇을 더 쉽게 하거나 피하고 싶은지, 사용자가 실제로 반복하는 행동과 명시한 제약을 찾는다.
2. 현재 방법이 그 결과를 직접 만드는지 확인한다. 사용자의 행동을 더 잘 표현하는 기능이나 업무 방식이 있으면 하나만 고른다. 새 제안이 단순해 보이는지만으로 추천하지 않는다.
3. 그 가설을 뒷받침하는 관찰을 찾고, 두 방향 중 하나를 고르게 할 질문이나 작은 확인 방법을 정한다. 자료로 확인할 수 있는 것은 먼저 확인한다.
4. 근거가 약하거나 다른 선택이 실제 행동을 바꾸지 않으면 속삭임을 만들지 않는다. 현재 방향이 맞으면 그 이유를 짧게 말한다.

## 어떻게 말하나

강한 가설이 있을 때는 **"혹시 원하시는 건 A가 아니라 B 아닐까요?"**처럼 한 문장으로 건넨다. 이어서 그렇게 생각한 근거와 방향을 가르는 질문 또는 다음 행동을 짧게 붙인다. 여러 약한 가설로 목록을 채우거나, 사용자의 의도를 확정하지 않는다.

예를 들어 "셀렉트 리스트의 위계를 저장해 줘"라는 요청에서 중요한 항목을 위로, 보고 싶지 않은 항목을 아래로 보내려는 행동이 보인다면:

> 혹시 필요한 건 항목마다 정확한 순서를 매기는 기능보다, 자주 쓰는 것은 쉽게 찾고 보고 싶지 않은 것은 숨기는 기능 아닐까요? 그렇다면 즐겨찾기와 숨김이 맞을 수 있습니다. 중간 항목끼리의 순서도 중요한지 확인해 보면 방향이 갈립니다.

"매일 대시보드를 열어 수치를 확인하자"는 작업에서 실제로는 이상 징후가 생겼는지만 확인한다면:

> 혹시 매일 화면을 여는 일보다 이상 징후를 제때 알아채는 게 목표 아닐까요? 정상일 때도 수치를 직접 봐야 하는지 확인하고, 아니라면 알림을 먼저 검토할 수 있습니다.

기본 결과는 방향 제안이다. 방향 점검만 요청받았다면 파일을 바꾸지 않는다. 사용자가 선택과 구현까지 맡겼다면 기존 제약과 승인 범위 안에서 이어서 수행한다. `.⚡wow`는 목표를 유지하며 설계를 다시 보고, `.⚡true`는 그 목표에 대한 가설부터 점검한다.
