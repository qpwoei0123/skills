# wow

기존 구현의 문제 정의와 설계 모델을 다시 보고, 삭제되는 개념이 분명한 재설계안을 제안한다. 코드 줄이기나 이름 정리가 아니라 "처음부터 이렇게 생각했어야 했다"는 관점 전환이 목표다.

## 계약

- 파일을 수정하거나 커밋하지 않는다. 실행 플래그도 제공하지 않는다.
- 사용자가 얻는 동작 목표는 유지하되 기존 구조는 전제로 삼지 않아도 된다.
- 새 추상화를 자랑하는 제안보다 상태·흐름·책임이 사라지는 제안을 우선한다.
- 적용은 사용자가 제안을 고른 뒤 별도 수정 작업으로 다룬다.

## 호출과 경계

```text
/wow
```

- 문제 정의나 설계 모델을 다시 보려는 요청은 `wow`가 맡는다.
- 기존 설계 안에서 동작을 유지하며 덜고 엮는 요청은 `trim`이 맡는다.
- 화면의 시각·UX 품질 개선은 `impeccable`이 맡는다.
- 재설계와 구현을 함께 요청해도 `wow`는 제안 단계만 소유한다. 사용자가 안을 고르기 전에는 구현으로 넘어가지 않는다.

## 분석

1. 사용자가 지정한 파일·기능·모듈을 우선 읽는다. 지정이 없으면 현재 diff를 보고, 둘 다 없으면 범위를 질문 하나로 묻는다.
2. 사용자 결과, 핵심 도메인 개념, 현재 상태·파일·흐름·API 표면을 정리한다.
3. 조건이 몰린 곳, 상태 동기화, 여러 레이어가 같은 결정을 반복하는 곳에서 현재 설계의 착각을 찾는다.
4. 문제를 더 적은 개념으로 다시 정의하고 상태·데이터 소유권·책임 위치를 재배치한다.
5. 강한 제안 1~4개만 남기고 가장 좋은 하나를 추천한다. 개수를 채우려고 약한 제안을 만들지 않는다.

## 제안 판정

좋은 후보:

- 여러 boolean과 동기화 로직을 하나의 도메인 상태로 바꿈
- 단계별 UI 흐름을 상태 전이, route, URL, 서버 상태로 다시 모델링함
- 여러 레이어의 중복 결정을 한 소유자에게 돌림
- 직접 만든 캐시·큐·라우팅을 검증된 플랫폼 기능으로 대체함
- helper를 정리하는 대신 helper가 필요 없는 데이터 흐름을 만듦

모든 제안은 두 검사를 통과해야 한다.

1. **삭제 테스트:** 사라지는 상태, 분기, 파일, 책임을 구체적으로 말할 수 있는가?
2. **엣지 케이스 재생:** 현재의 까다로운 사례 2~3개가 새 모델에서 자연스럽게 처리되는가?

변수명 변경, helper 추출, 단순 중복 제거, 파일 이동, 검증 방법 없는 대형 아키텍처는 출력하지 않는다. 제안 밀도는 [references/example.md](references/example.md)를 따른다.

## 출력

```text
WOW 제안

1. <제안 제목>
   - 지금 설계의 착각:
   - 더 좋은 문제 정의:
   - 새 설계 모델:
   - 삭제되는 개념:
   - 사용자는 무엇을 그대로 경험하는가:
   - 구현하면 바뀌는 구조:
   - 리스크:
   - 실험 방법:

가장 강한 추천
- ...
```

제목은 과감하고 구체적으로 쓰고, 각 제안에는 작은 실험 단위를 포함한다.

## 중단

아래에서는 제안 전에 필요한 질문 하나만 한다.

- diff나 대상 기능을 찾을 수 없음
- 제품 목표를 전혀 추론할 수 없음
- 유지해야 할 동작 범위가 불명확함
- 보안, 결제, 인증, 데이터 삭제 영역에서 오해 없이 제안할 핵심 제약이 없음
