# .⚡wow

현재 구조를 전제로 삼지 않고 문제를 더 단순하게 정의한다. 사라지는 상태·분기·책임이 분명한 설계를 찾는다.

## 요청과 범위

- `$.⚡wow`, `/.⚡wow`의 기본 결과는 제안이다. 대상은 사용자 지정 파일·기능을 우선하고, 없으면 현재 diff를 본다.
- 설계 제안만 요청했다면 파일을 수정하지 않는다. "보고 마음에 들면 구현"이면 선택을 기다린다.
- "좋은 안을 골라 구현까지"처럼 선택과 구현을 맡겼다면 추천 이유를 설명하고 같은 요청 안에서 일반 구현 작업으로 이어간다. 이미 맡긴 작업을 다시 승인받지 않는다.
- 기존 구조 안의 코드 정리는 `.⚡good`, 화면의 시각·UX 개선은 `impeccable`의 범위다. 단순 불만이나 화면 디자인 요청만으로 재설계를 시작하지 않는다.

## 설계 판단

사용자가 얻어야 할 결과와 유지할 동작을 먼저 이해한다. 그다음 조건이 몰린 곳, 상태 동기화, 여러 계층이 같은 결정을 반복하는 곳에서 불필요한 개념을 찾는다.

- 여러 boolean을 하나의 도메인 상태로 표현할 수 있는가?
- 같은 결정을 여러 곳에서 하는 대신 한 곳이 책임질 수 있는가?
- helper를 더 만드는 대신 helper가 필요 없는 데이터 흐름으로 바꿀 수 있는가?
- 직접 만든 캐시·큐·라우팅을 현재 환경의 검증된 기능으로 대체할 수 있는가?

제안은 두 기준으로 판단한다.

1. 사라지는 상태, 분기, 파일 또는 책임을 구체적으로 설명할 수 있다.
2. 현재의 까다로운 사례를 새 모델에서도 처리할 수 있고 확인할 작은 실험이 있다.

가장 강한 안을 추천한다. 강한 안이 하나면 하나만 제시하고, 약한 대안으로 개수를 채우지 않는다. 이름 변경·파일 이동·단순 helper 추출만으로 끝나는 안은 제외한다. 제안의 구체성은 [references/example.md](references/example.md)를 참고한다.

## 보고

현재 문제가 생기는 이유에서 새 모델로 자연스럽게 이어 설명한다. 삭제되는 복잡성, 유지되는 사용자 동작, 중요한 위험과 가장 작은 확인 방법을 포함한다. 고정된 보고서 항목을 반복할 필요는 없다.

대상이나 핵심 제품 제약이 없어 결과가 크게 달라질 때만 질문한다. 자료로 확인할 수 있는 내용은 먼저 조사한다.
