# commit

현재 git 변경을 읽고 하나의 의도씩 검토 가능한 한글 커밋으로 만든다. 기본 호출은 계획만, `--go`는 계획에 따라 즉시 실행한다.

## 계약

- 사용자 지시 > 레포 기여 문서 > 최근 로그 > 이 스킬 기본값 순으로 따른다.
- 사용자가 이미 stage한 상태는 의도로 존중한다. 재구성이 필요하면 먼저 알린다.
- amend, revert, 커밋 이력 조회는 다루지 않는다.
- 커밋 권한과 승인 상태는 현재 요청에만 유효하다. 새 수정이 생기면 다시 요청받는다.
- secret, 충돌, 원인 없는 생성물처럼 위험한 변경은 커밋하지 않는다.

## 호출

```text
/commit
/commit --go
/commit -go
```

- 기본 호출은 커밋 단위, 메시지, 검증 계획을 제안하고 멈춘다.
- `--go`, `-go`는 승인 질문 없이 같은 계획을 실행한다.

## 연계 요청 소유권

- 커밋만 요청받으면 `commit`이 전체 작업을 맡는다.
- "커밋하고 PR까지"처럼 PR/MR 생성도 요청받으면 `mr`이 전체 흐름을 맡는다. `mr`이 이 스킬 절차로 커밋을 끝낸 뒤 push와 draft 리뷰 요청을 이어간다.
- PR/MR만 요청받으면 `commit`을 자동 실행하지 않는다. dirty worktree 처리는 `mr`의 선택 흐름을 따른다.

## 분석

1. git repo인지 확인한다. 아니면 가장 가까운 후보를 찾고, 여러 개면 묻는다.
2. `scripts/collect_context.sh`로 status, 최근 로그, staged·unstaged stat, untracked, 기여 문서 후보를 읽는다. 모두 비어 있으면 "커밋할 변경 없음"으로 종료한다.
3. CONTRIBUTING, commitlint, commit template의 규칙을 확인한다.
4. stat을 보고 필요한 파일 diff와 untracked 내용만 읽는다. 여러 영역이면 파일·디렉터리·의도별로 분할 후보를 만든다.
5. 최근 커밋 3~5개에서 scope, 언어, 제목 길이, 본문 습관을 확인한다. 로그가 없으면 기본 규칙을 쓴 이유를 남긴다.

## 분할과 순서

- 하나의 커밋에는 하나의 의도만 담는다.
- 기능, 버그, 리팩터링, 문서, 설정이 독립적으로 검토·되돌리기 가능하면 나눈다.
- 코드와 대응 테스트, schema와 사용처, manifest와 lockfile처럼 한쪽만으로 깨지는 변경은 묶는다.
- 한 파일의 hunk가 안전하게 분리되지 않으면 억지로 쪼개지 않는다.
- 기반 변경 → 사용처 → 문서 순으로 두고, 어느 커밋에서 멈춰도 레포가 깨지지 않게 한다.

## 메시지

기여 문서가 다른 형식을 요구하지 않으면 다음 형식을 쓴다.

```text
<type>[(<scope>)]: <한글 요약>
```

- `type`: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `build`, `ci`, `perf`, `style`, `revert`
- 최근 다수 커밋이 scope를 쓰고 변경 영역이 명확할 때만 scope를 붙인다.
- 요약은 무엇을 만졌는지가 아니라 무엇이 달라지는지 쓰고 마침표를 붙이지 않는다.
- 이유나 검증 설명이 꼭 필요할 때만 짧은 한글 본문을 추가한다.

## 응답 형식

```text
커밋 계획
- 기여 문서: <경로와 반영 규칙 | 없음>
- 참고한 최근 커밋: <hash title> ...
- 채택한 스타일: <scope/본문/언어 판단>

1. <message>
   - 파일:
   - 이유:

검증
- 실행 예정:
- 생략:

후속 작업
- 자동 커밋 없음
- 다음 커밋은 다시 요청받음

이대로 커밋할까요?
```

## `--go` 실행

1. 위험 파일과 충돌 상태를 확인한다.
2. 단위별 필요한 파일만 stage한다. 전체가 한 의도일 때만 `git add -A`를 쓴다.
3. hunk 분리가 필요하면 비대화형 patch를 만들어 `git apply --cached`로 stage한다. 안전하지 않으면 파일 단위로 묶는다.
4. 계획에 적은 빠른 lint·test만 실행한다. 대응 명령이 없으면 생략 이유를 기록한다.
5. 제목만 있으면 `git commit -m`, 본문이 있으면 임시 메시지 파일과 `git commit -F`를 쓴다.
6. hook 실패를 `--no-verify`로 우회하지 않는다. hook이 파일을 고쳤다면 재stage 후 한 번만 재시도한다.
7. 각 커밋 뒤 남은 변경을 확인하고, 마지막에 해시·메시지·검증을 보고한다.
8. commit intent를 종료한다. 다음 작업은 새 요청 없이는 커밋하지 않는다.

## 중단

- merge, rebase, cherry-pick 충돌 상태
- secret, credential, 개인정보 정황
- 요청과 무관한 대규모 변경을 분리할 수 없음
- 생성물·lockfile만 바뀌고 원인 변경이 없음
- submodule, 대형 바이너리, 무관한 대량 삭제가 섞임

중단할 때는 문제 파일, 이유, 가능한 다음 행동만 짧게 보고한다.
