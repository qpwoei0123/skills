# commit

변경을 하나의 의도씩 검토하고 되돌릴 수 있는 로컬 이력으로 남긴다.

## 요청과 범위

- `$commit`, `/commit`, "커밋해줘"는 커밋까지 완료한다. "메시지만", "계획만"이면 제안까지만 한다. `--go`, `-go`도 실행 표기로 받으며 명시된 계획·범위 제한을 우선한다.
- 현재 요청과 그 후속 정정의 승인은 완료까지 유지한다. 완료 후 다른 작업을 새 요청 없이 자동 커밋하지 않는다.
- 사용자 지시 → 저장소 기여 문서 → 최근 로그 → 스킬 기본값 순으로 따른다.
- 이미 stage한 상태를 의도로 존중한다. 재구성이 필요하면 이유를 알리고, 포함 범위가 달라지는 모호함만 묻는다.
- PR/MR까지 요청했다면 `mr`이 이 절차로 커밋한 뒤 제출을 이어간다. 커밋만 요청했으면 로컬 이력에서 끝낸다.

## 변경 읽기

`scripts/collect_context.sh`로 status, 최근 로그, staged·unstaged stat, untracked와 기여 문서 후보를 한 번에 확인할 수 있다. 필요한 diff와 untracked 내용을 읽고 CONTRIBUTING, commitlint, commit template과 최근 메시지의 관례를 확인한다.

대상 변경이 없으면 그대로 보고한다. 다른 작업이 섞였으면 요청 범위를 먼저 분리하고, 안전하게 분리할 수 없는 경우에만 범위를 묻는다.

## 분할과 메시지

- 하나의 커밋에는 하나의 의도를 담는다. 독립적으로 검토·되돌릴 수 있는 변경은 나눈다.
- 코드와 대응 테스트, schema와 사용처, manifest와 lockfile처럼 함께 있어야 동작하는 변경은 묶는다.
- hunk를 안전하게 분리할 수 없으면 억지로 쪼개지 않는다. 의존하는 기반 변경을 먼저 두고 각 커밋이 일관된 상태를 유지하게 한다.
- 별도 관례가 없으면 `<type>[(<scope>)]: <한글 요약>`을 쓴다. scope는 저장소가 쓰고 변경 영역이 분명할 때 붙인다.
- 제목에는 달라지는 결과를 적는다. 이유나 검증 설명이 필요한 경우에만 짧은 본문을 추가한다.

## 실행

1. 충돌 상태, 비밀 정보와 요청 밖 변경을 확인한 뒤 단위별 필요한 파일만 stage한다. 전체가 같은 작업 범위일 때만 `git add -A`를 쓴다.
2. hunk 분리가 필요하면 비대화형 patch와 `git apply --cached`를 사용한다.
3. 현재 코드에 유효한 기존 검증 결과를 재사용하고, 추가로 필요한 관련 검증만 실행한다.
4. 제목만 있으면 `git commit -m`, 본문이 있으면 임시 메시지 파일과 `git commit -F`를 사용한다.
5. hook 실패를 `--no-verify`로 우회하지 않는다. hook이 수정한 내용을 확인해 요청 범위의 변경만 다시 stage하고 재시도한다. 같은 실패가 반복되면 원인을 보고한다.
6. 남은 변경을 확인하고 해시·메시지와 필요한 검증 결과를 간결하게 보고한다.

진행 중인 merge·rebase·cherry-pick 충돌, 노출될 비밀 정보, 원인을 설명할 수 없는 생성물이나 요청 밖 변경이 있으면 해당 커밋을 멈추고 문제와 다음 행동을 알린다. 파일 종류만으로 무조건 추가 승인을 요구하지 않는다.
