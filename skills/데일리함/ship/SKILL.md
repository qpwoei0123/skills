## 공통 판단 기준

현재 요청과 이 스킬의 작업 범위 안에서 관련 있는 기준만 적용한다. 규칙을 충족하려고 요청 밖 수정이나 형식적인 보고 항목을 추가하지 않는다.

제출할 커밋 범위와 설명에 필요한 의존 변경을 확인하는 데 사용한다. 남겨둔 변경 없이 제출 내용이 성립하는지 확인하고, 재설계로 확대하지 않는다.

### 함께 변경되는 단위 파악하기

같은 정책을 바꿀 때 반드시 함께 수정되어야 하는 부분을 찾는다. 코드와 사용처·설정·검증·공유 상수의 관계를 확인하고, 한쪽만 변경되면 깨지는 단위를 함께 다룬다. 모양이 비슷하다는 이유만으로 같은 변경 단위라고 판단하지 않는다.

# .⚡ship

`.⚡commit`의 연장선에서 현재 작업을 리뷰 가능한 변경과 설명으로 묶는다. 작업 폴더를 비우는 대신, 이번에 제출할 범위를 정확히 정한다.

사람이 결정할 리뷰 질문을 추리는 작업은 `.⚡review`의 범위다.

## 요청한 완료점

- `$.⚡ship`, `/.⚡ship`, "PR 준비해줘"는 필요한 변경을 커밋하고 실제 검토 가능한 제목·본문안을 만든다.
- "계획만", "수정하지 말고"이면 파일·git·원격 변경 없이 범위와 커밋 계획, 제목·본문안을 제안한다. 실행하지 않은 변경은 계획이라고 밝힌다.
- "기존 커밋만", "본문만"이면 새 커밋 없이 지정한 커밋 범위로 준비한다. 원격 본문만 갱신하는 요청은 해당 PR/MR의 원격 head를 기준으로 삼는다.
- push·PR/MR 생성·갱신을 요청했거나 같은 작업에서 이미 맡겼다면 그 범위까지 완료한다. `--go` 같은 추가 표시는 필요하지 않다. 완료한 다른 작업의 발행 권한을 새 작업에 적용하지 않는다.
- 코드 정리는 요청받았을 때 `.⚡good`으로 수행한다. 제출을 위해 재설계나 테스트 정리를 자동으로 추가하지 않는다.

## 대상과 관례

현재 git 상태, staged·unstaged·untracked 변경과 사용자 요청을 읽는다. `scripts/preflight.sh`로 읽기 전용 개요를 모을 수 있다. AGENTS·기여 문서, 커밋 관례, PR/MR 템플릿과 필요한 최근 본문에서 범위와 표현을 정한다.

플랫폼과 source/head·target/base 저장소를 식별한다. 같은 source repository와 head branch의 열린 PR/MR이 있으면 그 대상과 target branch를 사용하고, 새 요청을 중복 생성하지 않는다. 사용자 지정 base와 기존 target이 다르면 조용히 바꾸지 않는다.

새 요청의 base는 사용자 지정 → `branch.<name>.gh-merge-base` → 원격 기본 branch → `main` → `master` 순으로 확인한다. 현재 branch의 원격 추적 ref를 base로 쓰지 않는다. base가 불명확하면 비교를 꾸며내지 말고 필요한 정보만 확인한다.

원격 조회와 push에는 이미 인증된 `gh`·`glab`과 CLI 인증을 사용할 수 있는 HTTPS 경로를 우선한다. 인증이 없어도 확인 가능한 로컬 범위와 본문안은 준비한다. 원격 URL·전역 git 설정을 임의 변경하거나 SSH를 먼저 시도하지 않는다. 브랜치 이름이 실제 제출 규칙과 충돌할 때만 [브랜치 관례](references/branch-conventions.md)를 읽는다.

## 변경 선별과 커밋

커밋이 필요하면 `.⚡commit`의 지침을 적용한다. 사용할 수 없는 환경에서는 저장소 관례에 따라 변경을 의미 단위로 나누고, 각 커밋에 요청한 내용만 담는 기준을 따른다.

- 무관한 작업, 실험 중인 코드, 설명되지 않은 생성물 등은 맥락을 보고 남겨둘 수 있다. 남은 diff 자체를 중단 사유로 삼거나, 전부 커밋·되돌리기해서 작업 폴더를 비우지 않는다.
- 이미 staged인 변경도 실제 요청 범위와 대조한다. 다른 작업의 staged 변경을 함께 커밋하거나 사용자의 staging 의도를 잃지 않게 한다.
- 제출 범위를 독립적으로 분리할 수 없다면 관련 범위를 다시 정하고, 판단할 수 없는 부분만 묻는다.
- 검증은 실제 커밋할 내용에 적용되어야 한다. 남겨둔 변경이 있어야 통과하는 결과를 제출 범위의 검증으로 보고하지 않는다. 유효한 기존 결과를 재사용하고, 코드가 달라졌거나 확인할 문제가 있을 때만 관련 검증을 실행한다.

커밋할 변경이 없으면 기존 커밋으로 이어간다. base 대비 변경도 없으면 제출할 변경이 없다고 끝낸다. 충돌·비밀 정보·요청 범위의 검증 실패는 해결하거나 해당 부분을 보류하고, 이미 성공한 단계를 일괄 되돌리지 않는다.

## 제목과 본문

커밋을 마친 뒤 `<base>..HEAD`의 이력과 `<base>...HEAD`의 diff를 읽는다. 제목과 본문은 이 최종 범위를 설명하며, 남겨둔 미커밋 diff를 제출한 것처럼 쓰지 않는다.

제목·본문을 쓰거나 갱신하기 전에 [본문 작성 기준](references/review-format.md)을 읽는다. 리뷰어가 이해해 가는 순서를 우선한다. 기존 저장소 양식과 말투 안에서 필요한 배경, 변경과 결과, 판단할 지점이 자연스럽게 이어지도록 쓴다. 과거 초안이 있으면 최종 범위에 맞춰 다시 쓴다.

새 Draft에서 `.⚡ship`이 작성한 요약·검증·리뷰 설명은 `<!-- ship:managed:start -->`와 `<!-- ship:managed:end -->` 사이에 둔다. 기존 Draft의 표식과 사용자 작성 내용은 [본문 갱신](references/draft-update.md) 기준으로 보존한다.

기본 완료점은 필요한 커밋과 완성된 제목·본문안이다. 남긴 diff와 이유는 사용자에게 짧게 알리고 PR/MR 본문에 작업 일지처럼 넣지 않는다.

## 요청받은 원격 작업

원격 변경 직전에 source/head·base와 열린 요청을 다시 확인한다. 다른 사람의 새 커밋이나 본문 수정을 덮지 않는다. branch rename·force push·merge는 이 흐름에 포함하지 않는다.

- **push만:** 확인한 저장소의 현재 branch를 push하고 remote head SHA를 확인한다. 거절되면 force push하지 않는다.
- **새 Draft 생성:** 완성된 제목·본문을 준비하고 현재 branch를 push한다. 이후 같은 source/head의 열린 요청이 없는지 다시 확인한 뒤 Draft로 생성한다. 본문은 파일이나 구조화된 입력으로 전달한다. 실제 CLI 도움말로 Draft·base·head 옵션을 확인하고, Draft를 보장할 수 없으면 일반 요청으로 바꾸지 않는다.
- **기존 Draft 갱신:** [본문 갱신](references/draft-update.md)에 따라 기존 내용과 상태를 보존하며 필요한 push와 본문 변경을 수행한다. 원격 갱신을 요청하지 않았다면 수정안만 제공한다.

제출할 source branch가 detached HEAD·기본 branch이거나 원격 대상이 불명확하면 원격 작업 전에 해소한다. 기존 요청이 일반 PR/MR이면 새 Draft를 만들거나 상태를 바꾸지 않고 준비한 안과 URL을 보고한다.

완료된 커밋, 제목·본문안 또는 실제 Draft URL, 필요한 검증 결과와 남긴 diff를 간결하게 알린다. 실패했다면 실제 완료한 commit·push·본문 갱신을 구분한다. 생성·갱신을 완료했다고 하기 전에 대상, Draft 상태, remote head SHA와 본문 반영을 확인한다.
