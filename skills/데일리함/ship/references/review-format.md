# 리뷰 요청 제목과 본문

PR/MR 본문은 리뷰어가 변경을 이해하고 판단하는 인터페이스다. 이 대화를 모르는 동료가 읽으며 이해해 가는 순서를 우선한다. 필요한 배경을 먼저 주고, 변경과 결과를 연결한 뒤, 판단할 지점을 드러낸다. 독자가 파일·로그·이전 대화를 오가며 맥락을 조립해야 하는 부담을 줄인다.

## 저장소 양식

사용자 지시와 기여 문서를 우선하고, 실제 PR/MR 템플릿의 항목명·순서·필수 항목을 따른다. 템플릿으로 정해지지 않은 말투와 상세도는 최근의 관련 PR/MR 본문을 직접 읽고 맞춘다. 읽지 못한 자료를 참고했다고 주장하지 않는다.

이해의 흐름을 고정된 섹션으로 강제하지 않는다. 기존 양식 안에서 문장과 설명의 순서를 조정한다. 작성 편의를 위해 별도 양식을 덧씌우거나, 빈 항목과 체크리스트를 늘리지 않는다.

## 제목

별도 관례가 없으면 `<type>[(<scope>)]: <한글 요약>`을 쓴다. scope는 저장소가 쓰고 변경 영역이 분명할 때 붙인다. 대표 커밋의 문장을 그대로 복사하기보다 최종 변경 결과를 요약한다.

## 본문에 남길 내용

리뷰어가 “왜 필요한가”, “무엇이 달라지는가”, “어디를 보고 판단하면 되는가”를 앞 문장의 맥락으로 이해할 수 있게 쓴다. 낯선 개념은 필요한 배경과 함께 소개하고, 한 문단에서는 하나의 요점을 설명한다.

- **상황과 결과를 연결한다.** 어떤 조건에서 무엇이 문제였고, 변경 후 어떻게 달라지는지 설명한다. 작업한 파일이나 수행한 절차만 나열해서 독자가 의미를 추론하게 하지 않는다.
- **필요한 근거를 해석해서 전달한다.** 내부 식별자·도구 출력·작업 기록을 그대로 옮기지 않는다. 리뷰어의 판단에 필요한 경우에만 무엇을 뜻하고 변경과 어떤 관계인지 설명한다. 도구 화면에서 이미 확인할 수 있는 상태를 본문에 반복하지 않는다.
- **설명의 깊이를 변경에 맞춘다.** 작은 변경은 짧게 쓰고, 선택 이유나 호환성·운영 제약이 중요한 경우에만 배경을 더한다. 구체적인 동작을 설명하지 않는 완료 선언이나 막연한 품질 평가는 제거한다. 근거 없는 의도와 효과를 보태지 않는다.
- **확인할 행동을 제시한다.** 확인 방법에는 사람이 해볼 동작과 기대 결과를 쓴다. 코드·문서·설정 변경은 비교할 대상과 확인할 차이를 적는다. 필요한 검증은 수행하되 자동 검사 성공 내역을 나열하지 않고, 판단에 영향을 주는 실패·미확인 범위·제약을 밝힌다. 확인하지 않은 내용을 확인했다고 쓰지 않는다.

필수 항목도 이 기준으로 채운다. 사용자나 기여 규칙에서 특정 정보의 기재를 명시적으로 요구하면 필요한 범위에서 따른다.

제출 전에 처음 읽는 동료 입장에서 다시 읽는다. 설명보다 먼저 나온 용어·결론, 빠진 배경, 문단 사이의 논리적 단절을 보완한다. 그다음 이해나 판단에 기여하지 않는 문장을 덜어낸다. 짧게 만드는 것보다 독자가 추측하거나 되짚어 읽지 않아도 되는지를 우선한다. 본문을 API나 CLI로 전달할 때는 실제 개행을 보존한 임시 파일 또는 구조화된 입력을 사용한다.
