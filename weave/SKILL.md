# weave

흩어진 코드, 패턴, 책임을 한 곳에서 관리하기 좋게 엮는 스킬이다.
목표는 공통화 자체가 아니라 변경 지점과 개념 수를 줄여 응집도를 높이는 것이다.

## 불변 규칙

- 비슷해서 묶지 않는다.
- 같은 이유로 변하는 것만 묶는다.
- 애매하면 묶지 않는다.
- 동작을 바꾸지 않는다.
- 공개 API, 라우팅, 데이터 계약, 접근성 의미를 바꾸지 않는다.
- 작은 중복을 없애려고 큰 추상화를 만들지 않는다.
- 읽기 쉬운 로컬 코드를 멀리 보내지 않는다.

## 호출 형태

```text
/weave
/weave --go
/weave -go
```

- `/weave`: 현재 diff와 주변 구조를 분석하고 엮을 후보만 제안한다. 승인 전에는 파일을 수정하지 않는다.
- `/weave --go`, `/weave -go`: 승인 없이 낮은 위험도의 weave만 적용한다. feature 경계, public API, 의존성 방향이 바뀌는 후보는 계획으로만 남긴다.

## trim, wow와의 차이

```text
trim   = 덜어내고 다듬기
weave  = 흩어진 책임과 패턴을 엮기
wow    = 문제 정의를 새 관점으로 재설계하기
```

`trim`은 줄이는 것이 중심이고, `weave`는 모으고 맞추는 것이 중심이다.
`wow`는 관점을 바꾸는 제안이고, `weave`는 이미 있는 구조의 응집도를 높이는 작업이다.

## 분석 순서

1. 현재 repo와 diff 범위를 확인한다.
   - `git status --short`
   - `git diff --stat`
   - `git diff --name-only`
   - 필요하면 `git diff`
   - untracked 파일은 필요한 만큼 읽는다.
2. 변경 전 검증 명령을 찾는다.
   - test, lint, typecheck, build
   - 명확한 명령이 없으면 "검증 명령 없음"으로 기록한다.
3. 흩어진 책임과 반복 패턴을 찾는다.
4. 각 후보가 "같은 이유로 변하는가"를 판정한다.
5. import 방향, public API, 테스트 범위, 번들 경계, 라우팅/서버 경계, 스타일 우선순위 변화를 확인한다.
6. `/weave`면 계획을 제안하고 멈춘다.
7. `--go`면 낮은 위험도만 적용하고 같은 검증을 다시 실행한다.

## 엮을 후보

엮는 것이 매우 좋을 때만 제안한다.

- 같은 정책이나 규칙이 여러 파일에 반복됨
- 한 도메인의 타입, 상수, schema, formatter, mapper가 흩어짐
- 화면마다 로딩, 에러, empty 처리 방식이 제각각임
- 같은 역할의 helper나 hook이 이름만 다르게 여러 곳에 있음
- feature 내부 책임이 components, hooks, utils에 애매하게 분산됨
- export 방식, 파일명, 폴더명, 네이밍 규칙이 섞여 유지보수를 방해함
- 같은 변경을 할 때 여러 파일을 함께 고쳐야 하는 패턴이 보임
- 테스트 setup이나 fixture가 반복되어 변경 비용을 만든다

## 엮지 말 것

아래는 weave 대상이 아니다.

- 모양만 비슷하고 제품 의미나 변경 이유가 다른 코드
- 한 번만 쓰이는 코드를 공통화하는 것
- feature 경계를 넘어서 의존성을 꼬는 것
- 작은 중복을 없애려고 큰 추상화를 만드는 것
- 읽기 쉬운 로컬 코드를 멀리 보내는 것
- UI가 우연히 비슷할 뿐 사용 맥락이 다른 경우
- public API를 바꿔야 하는 공통화
- 순환 import나 역방향 의존성을 만드는 공통화
- 테스트만 통과하고 사람이 읽기 어려워지는 공통화

## 좋은 weave 기준

- 한 정책·규칙이 바뀔 때 둘 이상의 파일을 항상 함께 고쳐야 하면 같은 이유로 변하는 것이다. 한쪽만 따로 바뀔 수 있으면 묶지 않는다.
- 엮으면 변경 지점이 실제로 줄어든다.
- 개념 이름과 책임이 더 명확해진다.
- 사용처가 새 구조를 자연스럽게 읽을 수 있다.
- import 경로와 의존성 방향이 더 나빠지지 않는다.
- 테스트와 fixture도 함께 정리된다.
- 나중에 같은 정책 변경이 한 곳에서 끝날 가능성이 높다.

## `/weave` 응답 형식

```text
weave 후보

1. <후보 제목>
   - 흩어진 위치:
   - 공통으로 묶을 개념:
   - 왜 매우 좋은가:
   - 엮지 않으면 생기는 비용:
   - 엮을 때 줄어드는 변경 지점:
   - 사이드 이펙트 점검:
   - 위험도:

보류한 후보
- <왜 엮지 않는지>

검증
- 사전 실행:
- 사후 실행:
```

후보가 애매하면 "보류한 후보"에 넣고 엮지 않는 이유를 남긴다.

## `--go` 실행 규칙

`--go` 또는 `-go`가 있으면 다음 순서로 진행한다.

1. baseline을 기록한다.
   - `git diff --stat`
   - 가능한 검증 명령 결과
2. 낮은 위험도의 weave만 적용한다.
3. import, export, 테스트 fixture를 함께 정리한다.
4. 같은 검증 명령을 다시 실행한다.
5. 실패하면 원인을 파악해 고치거나, 방금 적용한 weave 변경만 안전하게 되돌린다. 기존 사용자 변경은 임의로 revert하지 않는다.
6. 최종 보고에는 엮은 개념, 이동/병합한 파일, 줄어든 변경 지점, 실행한 검증, 남긴 리스크를 포함한다.

## 중단 조건

아래 상황에서는 `--go`여도 수정하지 않는다.

- baseline 빌드나 테스트가 실패했고 실패 원인을 파악할 수 없음
- 같은 이유로 변한다는 근거가 약함
- feature boundary나 public API 변경이 필요함
- 의존성 방향이 나빠지거나 순환 import 위험이 있음
- 라우팅, 서버 경계, 번들 경계, 스타일 우선순위 변화가 큼
- 동작 보존을 확인할 방법이 없고 변경 위험이 보통 이상임
- 사용자가 만든 기존 변경과 weave 대상이 얽혀 있어 안전하게 분리할 수 없음

중단할 때는 이유와 다음 행동을 짧게 제시한다.
